## Ensayo y contrato operativo

`preservacion.py` ofrece `plan`, `export`, `import`, `restore` y `verify`. Importación y restauración consumen el mismo paquete de directorio CAS. La exportación y restauración requieren destino nuevo; nunca reparan ni reemplazan uno existente. Copian en flujo de 1 MiB, comprueban los bytes del destino y publican `manifest.json` al final mediante enlace exclusivo y fsync. Los objetos quedan 0444 y no son hardlinks al original. Esa inmutabilidad es del protocolo, no resistencia frente a un administrador que cambie permisos. No hay transacción conjunta ante escritura hostil concurrente; no usar destinos controlados por terceros.

`ensayo.json` registra exportación/restauración completas y comprobación de los 708 objetos. Después se altera un objeto restaurado y se elimina: ambas comprobaciones fallan; se repone desde bytes conservados de la copia y vuelve a verificarse el conjunto. Ningún original se toca. Se hicieron dos copias de 0,975 GB, una exportación y una restauración real, necesarias para probar ambos pasos; no se cargó el corpus en RAM. Se conservan en `.cache/procedencia/preservacion-en-preparacion/{paquete,restauracion}`. Esta promesa inicial queda corregida por PREV2-02: un fallo posterior al enlace puede dejar manifest.json visible con durabilidad indeterminada. Conservar el destino y consultar correcciones/preservacion-v3/INFORME.md; no interpretar presencia como éxito.

La raíz de confianza es el manifiesto revisado cuyo hash se fija fuera del paquete. Un atacante que sustituya manifiesto y blobs puede producir otro paquete internamente coherente: el verificador no acredita identidad del editor. No intercambiar el manifiesto confiado por el recuperado sin cotejar su hash.

## Transferencia propuesta al remoto existente

Remoto observado sin credenciales: `github.com:eliesgalvira/IRoboPF.git`; API GitHub confirma repositorio público, rama por defecto main, tamaño declarado 52.944 KiB. No existe `.gitattributes` local ni configuración `lfs.*` observada. El árbol remoto de `procedencia-documental` tampoco contiene `.gitattributes` o `.lfsconfig`. Esto no demuestra ausencia de objetos LFS huérfanos remotos; no se certifica ningún respaldo remoto previo. No hay dos copias fuera del equipo: GitHub sería un solo dominio de custodia; dos carpetas o repositorios allí no acreditan independencia.

Git ordinario trasladaría casi 1 GB a clones e historial. Objeción: cumplir el límite individual no hace adecuada esa distribución. Se descarta como opción recomendada; [GitHub recomienda repositorios pequeños](https://docs.github.com/en/repositories/working-with-files/managing-large-files/about-large-files-on-github).

La opción propuesta es CAS por objeto en LFS del **mismo repositorio**, con punteros bajo `corpus/sha256/` y manifiesto en Git normal. `lfs-pointers.json` deja los 708 contenidos de puntero exactos preparados (oid SHA-256 y tamaño). No agrupar todo en un tar monolítico: una incorporación obligaría a almacenar y descargar otra versión entera. Antes del primer envío, revisión independiente, comprobación de cuota libre y elección del padre.

[Documentación de facturación GitHub](https://docs.github.com/en/billing/concepts/product-billing/git-lfs): Free/Pro incluyen 10 GiB de almacenamiento y 10 GiB de descarga por ciclo, compartidos por cuenta; Team/Enterprise Cloud 250 GiB. Una restauración de este paquete consumiría 0,908 GiB de descarga. [Calculadora oficial](https://github.com/pricing/calculator): exceso a 0,07 USD/GiB de almacenamiento y 0,0875 USD/GiB de salida (aprox. 0,064 USD/mes y 0,079 USD por descarga completa si todo excediera la cuota). Las páginas comerciales conservan textos de transición/paquetes antiguos: prevalece comprobar la modalidad real de la cuenta. No se asume presupuesto nuevo. Con cuota disponible el incremento sería cero; **no se pudo comprobar la cuota disponible**: API de facturación devolvió 404 y pidió alcance `user`, que no se amplió. El padre debe ver uso y presupuesto en Settings → Billing; presupuesto cero evita sobrecoste pero puede bloquear descargas al agotar cuota.

[Límites LFS oficiales](https://docs.github.com/en/repositories/working-with-files/managing-large-files/about-git-large-file-storage): 2 GB por archivo Free/Pro, 4 GB Team, 5 GB Enterprise; este conjunto queda holgadamente por debajo. LFS no sirve directamente contenido GitHub Pages. Cada nueva versión cuenta completa y los lectores/Actions consumen salida: mantener descargas selectivas y no añadir el corpus a cada CI.

Bloqueo técnico concreto: [Jujutsu declara Git LFS no soportado](https://github.com/jj-vcs/jj/blob/main/docs/git-compatibility.md). `jj git push` de punteros no sube objetos. La vía viable necesita un paso explícito git-lfs/API separado para cargar los objetos por oid y después publicar los punteros con JJ; no activar filtros y esperar que JJ los ejecute. Secuencia propuesta al padre: (1) aprobar conjunto/cuota; (2) preparar almacenamiento LFS desde CAS, sin modificar los originales; (3) cargar objetos con cliente LFS autorizado; (4) publicar los punteros/manifiesto con JJ, al final; (5) recuperar todos los oids desde GitHub a un destino vacío y ejecutar `restore`/`verify` con el manifiesto confiado. La preparación de punteros está hecha, pero el adaptador autenticado LFS y la prueba real JJ/LFS siguen pendientes: no se entrega un supuesto uploader listo sin haberlo probado. No hay excepción implícita a la prohibición de mutar VCS ni autorización de este hijo para hacer esa carga.

Una segunda copia externa independiente requiere un medio ya disponible elegido por Elies (por ejemplo disco externo custodiado fuera del equipo u otro equipo autorizado); no se han asumido cuentas, permisos o cuotas nuevas. Hasta recuperar desde el remoto no se anunciará preservación externa conseguida. El padre tiene un paquete concreto y una restauración local comprobada para autorizar la siguiente fase.
