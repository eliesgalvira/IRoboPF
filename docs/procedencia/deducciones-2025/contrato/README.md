# Contrato de entrega y verificación

Contrato técnico revisado, con [correcciones contrastadas independientemente](../revisiones/contrato-corregido/INFORME.md). No emite dictámenes fiscales ni acepta los de otros lotes; esos paquetes siguen siendo candidatos hasta su revisión normativa.

Desde la raíz, con Node, Python 3 del sistema y uv disponibles (jsonschema 4.26.0 se resuelve en caché externa):

```sh
node scripts/procedencia/deducciones-2025/verificar.mjs --lotes docs/procedencia/deducciones-2025/lotes --modo parcial
node scripts/procedencia/deducciones-2025/verificar.mjs --lotes docs/procedencia/deducciones-2025/lotes --modo completo --cas "$CAS_EXTERNO" --formato sha256
```

`sha256` resuelve `ROOT/sha256/HASH`; `plano` resuelve `ROOT/HASH`. Ambos requieren root explícito externo al repositorio. El verificador solo lee, no descarga ni mueve bytes. Comprueba tamaño, SHA-256 y SHA-512 de cada documento recibido; detecta enlaces que escapen del root. Sin `--cas` informa `integridadBytes: no_comprobada`, también en modo completo. Cobertura completa e integridad son ejes separados: para exigir ambas en integración se debe pasar CAS. Un original ausente o alterado produce error al comprobar bytes.

El modo parcial admite lotes enteros aún no recibidos y devuelve sus códigos como pendientes. Cada lote recibido debe estar completo. El modo completo exige los 351 códigos exactos del censo, con comunidad y lote correctos; Ceuta y Melilla no añaden registros. La base de paquete es el commit exacto indicado en el encargo de implementación.

El JSON Schema `scripts/procedencia/deducciones-2025/contrato.schema.json` contiene `$defs.lote` y `$defs.fuentes` (Draft 2020-12). El consumidor usa `jsonschema` (Draft202012Validator) mediante `uv run --no-project --python python3 --no-managed-python --with jsonschema==4.26.0`; no crea un entorno dentro del repositorio. Se pueden fijar `UV_CACHE_DIR` y `UV_PROJECT_ENVIRONMENT` a ubicaciones externas; por defecto usa el directorio temporal del sistema. Para usar otro validador se selecciona la definición correspondiente con `$ref`. El schema exige todos los campos comunes; los arrays vacíos no fabrican evidencia. `pendientes` exige `causa`, `actuacionesRealizadas` (array no vacío) y `evidenciaNecesaria`.

Convenciones precisas: un localizador HTML usa `selector`, `inicio`, `fin` (rango semiabierto de caracteres) y `recetaExtraccion`; PDF usa página física desde 1 y bbox `[x0,y0,x1,y1]` en puntos. `manual.documentoId` referencia un documento de tipo manual, `manual.citas` solo citas a ese documento. `paginasFicha` conserva el censo; `paginasComprobadas` registra lo realmente contrastado. Las diferencias de paginación se explican en reservas. `vigencia.citas` y las listas anidadas `citas`/`citaIds` se contrastan con las citas locales. Las reservas pueden detallar reformas, transitorios, límites y remisiones todavía abiertos.

Los contraejemplos usan `entradas`, `esperado`, `calculoIndependiente`, `observado`, `apiOCampo`, `pruebaReproducible`, `alcance`. Los cambios usan `archivo`, `motivo`, `pruebaRojaAnterior`, `resultadoPosterior`. La comparación exige aspecto, valores, regla oficial, citas, resultado y motivo. Una diferencia exige comparación discrepante y discriminante reproducible. Un cambio entre dictamen anterior y posterior exige prueba/fix. Una coincidencia global no puede ocultar cálculo o ficha no verificables, y una diferencia de ficha/cálculo debe conservarse en el global.

Cada comparación es actual por defecto (`momento: "despues"`). Para conservar una diferencia anterior ya corregida se añade `momento: "antes"`, junto al cambio acreditado y una comparación actual del mismo `campoCodigo`. No se deduce ese estado de palabras en `motivo`. Una discrepancia actual exige global y al menos un dictamen de ficha/cálculo discrepantes; una comparación actual no verificable exige reserva concreta e impide el global coincidente. Una diferencia global actual no se puede justificar únicamente con diferencias históricas.

Los documentos requieren URL HTTPS sin credenciales, fechas, ambos hashes y metadatos editoriales. Su ID es local al lote; la referencia completa es `(lote, documentoId)`. Adquisiciones independientes pueden compartir contenido y conservar URLs y fechas distintas, sin fusionar ni sobrescribir sus registros. Para el mismo SHA-256 se exige igual SHA-512, tamaño y MIME. Dentro de un lote los IDs son únicos; puede haber varias adquisiciones del mismo contenido con IDs diferentes. Las citas deben apuntar a documentos declarados con MIME compatible y localizadores no vacíos. Se rechazan campos privados conocidos, rutas locales y firmas de originales embebidos. El filtro de URL analiza nombres de parámetros decodificados, sin distinguir mayúsculas, incluso en primera posición o sin valor. Este filtro no sustituye la inspección de privacidad: ni la sintaxis de una URL prueba su oficialidad ni un hash prueba el contenido de una cita. La titularidad oficial, reextracción literal desde PDF/HTML, correspondencia de artículos y efectos jurídicos requieren cotejo independiente. El verificador no ejecuta recetas arbitrarias de extracción ni pruebas mencionadas en los dictámenes.

La fecha editorial de un manual no acredita su publicación. Cuando esta última no se conoce, `fechaPublicacion` admite `null` únicamente para documentos de tipo `manual`, con `reservaFechaPublicacion` no vacía. `fechaEditorial`, si se conoce, registra por separado la fecha ISO del pie editorial. Las publicaciones normativas siguen exigiendo fecha acreditada. Una URL HTTPS completa puede contener segmentos como `/home/`; el filtro distingue esa URL de una ruta local. La revisión A corroboró ambos positivos y detectó dos defectos adicionales, ya corregidos: se comprueban credenciales en las URL de cualquier texto y el schema aislado restringe también las fechas nulas. [Cambios y contraste pendiente](../correcciones/contrato-url-fecha/CONTRASTE.md).

Para dictámenes positivos o diferencias actuales se exige publicación original, comparación, manual enlazado y vigencia enlazada. Son publicaciones primarias las de la norma inicial, sus reformas y sus correcciones (`original`, `reforma`, `correccion`); un consolidado o manual no las sustituye. Su pertinencia al artículo y sus efectos temporales requieren revisión normativa. Los `no_verificable` necesitan pendientes concretos con actuaciones: una ficha no investigada debe permanecer ausente como lote pendiente, no rellenarse con un dictamen artificial. El control estructural no puede probar que las actuaciones narradas se realizaron. El resultado siempre es `candidato` y `requiere_revision_independiente`.

Pruebas de contrato: `bun run test tests/deducciones-procedencia-2025-contrato.test.ts --maxWorkers=1`. Los fixtures son hipotéticos y no constituyen evidencia fiscal. Los bytes mínimos temporales se escriben fuera de Git y se conservan; no se toca ningún original existente.

Las [regresiones del consumidor](regresiones.py) cubren los tres defectos de la [revisión independiente](../revisiones/contrato/INFORME.md). Se ejecutan con `REVIEW_TMP` externo y `uv run --no-project --python python3 --no-managed-python --with jsonschema==4.26.0 python docs/procedencia/deducciones-2025/contrato/regresiones.py`. Conservan los casos de revisión, salvo que el positivo histórico añade el nuevo campo `momento: "antes"`; otro caso comprueba que la antigua representación solo textual se rechaza. Las pruebas y expectativas originales siguen disponibles sin modificación para reproducir la versión anterior.

En NixOS, si faltan ejecutables en PATH, ejecutar dentro de `nix shell nixpkgs#nodejs nixpkgs#python3 nixpkgs#uv` (y `nixpkgs#bun` para pruebas). No se usan intérpretes Python descargados por uv.
